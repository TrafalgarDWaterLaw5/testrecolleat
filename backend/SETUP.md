# Build 4.3 — account backend setup (private beta only)

This package preserves the existing offline journal. It contains a deployable Supabase account and friend service, not a hosted account service. Until configured, the account panel is unavailable and no account data is transmitted.

1. Create a dedicated Supabase project in an appropriate region. In Authentication enable email/password and email confirmation, set minimum password length to 12, configure production email delivery, rate limits, CAPTCHA if needed, and site/redirect URLs for your actual HTTPS domain. Test verification delivery. Disable unneeded providers. Do not enable anonymous auth. Configure recovery/support before beta (password reset is not implemented in this client).
2. Run `backend/schema.sql` once in the project's SQL editor as postgres. Keep `reco_private` out of exposed schemas. Only the public RPC is exposed. No Storage buckets are needed. Never upload journal photos to Supabase at this stage.
3. Set `account-config.js` to the project HTTPS URL and public publishable or legacy anon key. Never use a service-role key or secret. Deploy the static files as with Build 3.5. Backend SQL is excluded by .assetsignore for Cloudflare; also exclude backend/ from any other public host. The SQL contains no secrets.
4. Sign up, verify email, sign in, and create your display name. In SQL editor manually run `insert into reco_private.admins(id) select id from auth.users where email='YOUR_VERIFIED_EMAIL';` with your actual email. Refresh account state or sign in again. Do not give admin access to test users. Dashboard shows recent reports and accounts (up to 200 each), not journal content. For larger deployments add pagination, alerting and MFA for administrators; handle complaints via the listed support channel.
5. Test with two ordinary verified accounts and one founder account. Confirm pending requests are not friends; acceptance is required; block prevents new requests; remove revokes the friendship; ordinary users cannot run admin actions; account deletion removes the Auth user and relationships; stale tokens cannot invoke RPC; reports remain with removed account references. Try guessed IDs and unauthenticated RPC calls; verify direct table access fails. Confirm journal data is unchanged and no restaurant fields or photos are transmitted. Test offline journal separately. Sessions are held in memory, so refresh/reopening the app requires sign-in again. Set appropriate Auth rate limits and monitor abuse; no account or friendship data is cached locally by this module.
6. Before beta: verify live access controls, processor terms and transfer arrangements, retention/deletion of safety reports and audit logs, founder coverage, email support, account recovery, privacy/terms text, security review, and relevant legal duties. No independent security or compliance certification is implied. Report limits, connection limits, and a serialized mutation lock are starter controls for a small beta, not a large-scale architecture.

## Scope boundary
The account stores email/authentication, display name, invite code, accepted/pending relationships, blocks, reports and minimal enforcement/audit records. It does not store restaurant logs, ratings, photos, collections, or local profile photos. No friend feed or sharing is enabled. Local per-restaurant sharing drafts are saved only in journal preferences and do not publish anything. Actual per-item sharing, revocable photo access, and content moderation will require a separate opt-in sharing release with server-enforced policies; do not turn on public buckets. Existing local export and erasure controls remain available. Account deletion does not erase the device journal. Sign out does not erase it either. Protect access on shared devices.
